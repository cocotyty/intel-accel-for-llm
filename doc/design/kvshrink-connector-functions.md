# KVShrink Connector 逐函数讲解

这份文档回答一个问题：`kvshrink/kvshrink_connector.py` 里每个函数
为什么存在、为什么长这样。评审时按着它对照代码讲。

代码是单文件单类，和 main 的组织方式一模一样（一个
KVShrinkConnector，里面 Scheduler 和 Worker 两套方法），所以每个新增
的东西都能指着说"这是 hybrid 需要的"，而不是结构噪音。

先记住三条删改原则，后面所有"为什么删/为什么留"都回到这三条：

1. **会自然炸的检查就删。** 底下那行代码自己会报错，前面的 if 只是
   把报错信息换了个措辞。
2. **不会炸、但会悄悄算错数据的检查必须留。** 这类错误没有任何别的
   防线——比如 as_strided 读越界不会报错，只会把隔壁块的字节当数据用。
3. **操作员配置校验和 main 有的东西保留。** 配置错了要在启动时报错，
   不能等跑起来才发现。

--------------------------------------------------------------------
## 1. 先搞懂三个背景知识

**vLLM 的 group 模型。** v0.23 把模型的所有 KV cache 分成组：
纯 attention 模型就一组；Qwen3.5 这种 hybrid 模型有四组（一组
attention + 三组 GDN/mamba）。整个连接器只写"对一个组怎么办"的逻辑，
从不问"我是不是 hybrid"。一条路径，没有分叉。

**GDN 层的特殊性。** attention 层的 KV 是一块一块切的，切到哪都能
存能取；GDN（mamba）层是一个递归状态，只在特定 token 边界上有一个
完整快照可存可取。所以 attention 组按块搬运，mamba 组按边界整体搬
运，命中规则也不一样。

**保存和加载都有流水线。** 读：mamba 状态在 forward 开始前一次性等
好，attention 层的页在每层的入口 hook 才等（vLLM 对每个 attention
层都会调一次 `wait_for_layer_load`，对 mamba 层什么都不调）。
写：每个 attention 层跑完它的数据就是最终值了，当场提交异步写，
不等 forward 全结束。

## 2. 顶上的 dataclass：几个"记账本"

### ReqMeta —— 一个请求一步的全部搬运指令
worker 干活的最小单位。里面是每个组一条的搬运清单（搬哪些外部键到
哪些 GPU 块）。`external_hit_tokens` 记录核心这次接受了多少个不用重
算的 token，主要是给日志和 fail-closed 断言用的。后面两个字段管异
步加载，见到 `_decide_async` 再说。

### ReqGroupState / ReqState —— 调度侧给每个请求记的账
每组要记两样：GPU 块表副本（vLLM 分配了哪些块给我们）、增量保存游标
（存到第几块了）。请求级最值钱的是 `live_source`：它直接引用
vLLM Request 身上那个不断变长的列表。为什么？因为 vLLM 只在请求刚进
来时通知我们一次，之后请求边 decode 边完成的块**没有任何回调**会告
诉我们——只能自己盯着人家的列表看长了多少。snapshot_boundary 是查
询时定下的恢复点，后面建加载计划时只用这个数，绝不重新查一遍（重
新查会被中途状态污染，见 `_build_load_meta_from_state`）。

### KVShrinkConnectorMetadata —— 发给 worker 的包裹
调度侧决定的事全装这里面发过去：谁要读（reqs_to_load）、谁要写
（reqs_to_save）。worker 不接触任何调度侧簿记，只看这个包裹干活。

曾经有个 `add_request` 方便方法，删了：生产代码里根本没人调它，全是
测试在用。给测试开的生产 API 就是死代码，测试改成直接构造对象塞字
典。

## 3. 寻址体系：往 store 里放东西总得起名字

Store 里每份数据有三个坐标 (label, chunk_id, tensor_key)：

- `chunk_id` 是块的内容 hash；
- `tensor_key` 是层名；
- `label` 是组号，格式 `g{N}`。

为什么 label 必须带组号？因为存在性台账（Record）按 `(label,
chunk_id)` 记账、不带层名：attention 组和三个 mamba 组住在同一本账
里，同一个前缀 hash 在每个组都各有一份，不分组成一次落账会把别的组
的存在性也标记成"有"，命中判定直接失真。而层与层之间不用分——数据
键自带全模型唯一的层名。跨 rank 不需要任何键成分：每个 rank 持久化
到自己的 `{model}_rank{r}` 目录，controller 只开 rank0 那本；同标签
天然读写一致，连重映射函数都不需要。

这个寻址方案是"对齐 main"的最终形态：main 用裸 basename 进目录、
默认 "kv" 标签、零命名空间，我们只是把"一个默认标签"换成"每组一个
标签"。曾经有一套 sha256 的 compute_namespace（把 model/dtype/tp/
schema 版本拌进每个键），随同名独立 HybridStore 机制引入、机制删除后
成了孤儿，最终整个删掉——它防御的 dtype/tp 串味场景 main 一直裸奔，
单独给 hybrid 加锁不是本分支的职责。

PP!=1 依然在 `_init_kv_stack` 开头显式拒绝（PP 把模型的层切开到不
同 rank，每个 rank 只握半个模型的页却拿着完整的 key）。speculative
decoding 同理同款。

`lookup_boundary` 是"这个边界在不在店里"的一问。唯一一次故意吞异常
发生在这里，而且方向想清楚了才吞的：**错的 hit 会污染输出（大锅），
错的 miss 只赔一次重算（小钱）**，所以 store 打个喷嚏就一律当 MISS。
别的任何地方出错都是直接炸。

`CacheKey` 最终形态：(block_hash, group_idx, layer_name)。曾经还有
namespace / tp_size / rank 字段——namespace 整个机制删了见上；
tp_size 是 namespace 哈希的恒常量影子；rank 编进 label 的唯一作用是
让调度侧和 worker 的字符串在两边目录里各自相等，纯属自娱自乐，删掉
后 worker 端的重映射函数 `_worker_key` 也一起陪葬了。

## 4. 解析和校验：把 vLLM 的配置翻译成我们的结构

`parse_kv_cache_config` 把 vLLM 的 KVCacheConfig 拆成 groups、每层的
页面尺寸、全局块数。翻译时有一串"发现不对就拒绝"的关卡，每个都有
实际场景撑腰：

- 一组里混两种 spec -> 拒绝。一组的所有层在一次调用里为同一批块各
  出一个视图，要求组内页面形状一致，混了视图就没法一次写齐。
- 非 align 的 mamba 模式 -> 拒绝并告诉操作员加什么启动参数。非 align
  时 GDN 状态是一整块不按边界切的，根本没有东西可以拿来做快照。
  更阴的是 vLLM 关掉 prefix caching 时会偷偷把这个模式改写成 none，
  而 hybrid 模型默认关 prefix caching——所以这是最容易踩的坑，报错
  信息里直接把逃逸路径写出来。
- 各组块尺寸不一致 -> 拒绝。一个 block hash 要同时给所有组指路，尺
  寸不一致时这种对应关系只在其中一个组成立，其他组会静默错位。

`Canonicalizer` 是理解这个文件的钥匙。先把一个流传过的说法纠正掉：
引擎并**不**要求一次调用的张量同形同 dtype——它逐条目循环、每层独立
入账（flow.py 的 put 循环），全端上去也合法。真正的问题是可寻址性：
一个 GDN 层天生是一个存储上的两个异形张量（conv 态 + ssm 态），谁
也没法当"块表的行"来切片搬运。Canonicalizer 给每层做一个统一的
(num_blocks, page_bytes) int8 视图后，一切张量都变成"沿 dim0 按块号
寻址的字节行"，整个引擎接口被拉平。另外三个职责：

- **为什么一组一次调用**：不是形状，是 label 契约——显式 label 的调
  用会被整体记账结算（写即提交），所以一次调用必须恰好端齐一个组的
  全部层；把四个组一锅端等于用一个调用结算四本只写了一部分的账页。

- **split-K/V 探测**。某些 attention 布局下块的 K 和 V 在显存里不相
  邻，平铺视图会 stride 到错误的字节——照样不炸不报错，搬回来的数
  据是别处的垃圾。所以探测命中时要拆成 K/V 两个半页视图。（这条注
  释之前写的 [2,N,...] 布局在 v0.23 已经不对了，注释已修正，判定算
  法本身跟布局顺序无关、不受影响。）
- `get_page` 和 `_page_parts` 删掉了。它们在生产里唯一的用户是个调
  试转储函数，剩下的调用者全是测试。统一走 `page_view_parts` 一条
  路：少两个函数，调试看到的字节就是引擎真正搬动的字节，还省了每
  页一次 torch.cat 拷贝。

## 5. 命中检测：把 vLLM 的问题拿来问自己的店

`HybridHitPolicy` 做的事情很妙：vLLM 有现成的"最长命中前缀"匹配代
码，它会问块池"这个 hash 缓存了吗"。我们造了个假的块池
（`_StoreAsBlockPool`），把这个问题的答案从"问 GPU 池"换成"问外部
store"，其余一行上游代码都不抄。抄的结果只有一个：上游哪天改了规
则，我们悄悄跟不上。

组合的多轮收敛也是必要的：attention 组命中不代表 mamba 组有任何东
西，每组单独查、互相收紧，直到稳定为止。mamba 侧还要对齐 down 到
align_size，最后一个 prompt token 永远重算（logprobs 和 state 要用）。

返回给 vLLM 的类型从基类的 `int|None` 收窄成 `int`：我们的查找是同
步的，None（延迟应答）在我们这里不可能出现。诚实签名比宽容签名更
容易审。

## 6. Scheduler 侧方法：只做计划，不动一根手指

整体流程四步，都在横幅注释里有图：新请求来了先查询（我们店里能赔
多少 token）-> 分配完块后记录 -> 步末打包计划发 worker -> 请求死亡
销账。下面挑有故事的说。

**`on_cached_request`（running 请求的唯一联络方式）**干两件事：
吸收新分配的块 id；回滚保存游标。回滚是重头戏：游标的语义是"这些
块的保存已经确定不需要再发了"。预占恢复（resume）时之前的发可能根
本没落地，进度倒退也一样可疑——这时把游标卷回去重发。重发是幂等
的（写两遍无害），漏发是永久的（那个边界永远丢了还没人知道）。两
害相权，宁可多干活。

**`update_state_after_alloc` 只记录、不建计划**，三个理由写在
docstring 里，概括成一句：在这里建计划会把逻辑复制出第二条路径，而
真正的恢复点早在查询时就定死了。这一段里原来的越界 continue 也删
了：vLLM 给的块表和我们手里的组数来自同一份 config，长度永远相等，
那个分支不可达；更要命的是它遇错的处理是跳过而非报错，真发生了会
拿着半张块表继续跑。

**`request_finished` 返回 (True, None)：延迟释放块。** 故事线：异步
写还在读那些 GPU 块呢，这边把块标记为空闲，下一个请求立刻覆写它，
异步写就把垃圾发给店了。全程无声。所以块释放推迟到 get_finished 里
确认"读它们的写全部落地"才上报。

**Mamba 加载为什么要写 CURR 槽、还只写一个槽** —— 这是最长的论证，
浓缩版：v0.23 的内核执行时不扫整张块表，而是算出一个下标、只 gather
那一列。这个下标我们能精确算出来。早年版本 prev/curr 双写是因为那
时没吃透 preprocess_mamba 的拷贝时机，多写一个是死功；读了 v0.23 源
码坐实后砍成了单槽。配套的槽位合法性检查留下（错槽 = 内核读到没恢
复的状态 = 错 token 且无声），scheduled_tokens 为零的同路径 fail-stop
也留（那条路上 start_load_kv 根本不会跑，槽永远补不上，而 core 已经
把这些 token 记作不用算了——进 forward 就是拿未恢复的状态生产出错
的答案）。异步请求在这里是例外，例外本身也有推导，太长不展开，全
在注释里。

**`_decide_async` 决定要不要异步加载**。并发的近似就是当前活着的请
求书数目。这里有个 clamp 保命细节：配置要求"前 N 层落地就放行"如
果 N 大于模型的总层数，这个条件永远达不到，请求会卡在等待队列里一
辈子——所以超界折叠成"等全部"。早先版本这里还有个 except Exception
静默降级，删了：配置错了就该在配置处炸，烂配置静默变成同步模式只
会让性能凭空消失而没人知道为什么。

**`build_connector_meta` 顺序敏感**：正在跑的请求的块表同步必须先
于生成保存计划，否则这一步新分的块赶不上这一步的保存。resume 请求
走第三条门（他们不在 new 列表里，藏在 cached_reqs.resumed_req_ids
里，vLLM 的怪癖，漏了=预占后输出乱码）。

## 7. Worker 侧方法：真正动手的人

**注册三件套**（`register_kv_caches` + `register`）：FlashInfer 拒绝
（它的 gather 语义不一样，没法安全支持）；给每层建规范视图并弄清楚
执行顺序（vLLM 递过来的字典是按组灌的，顺序打乱了，我们从层名的编
号里恢复排序——vLLM 自己 bind_kv_cache 也是这么干的，这个顺序是后
面"前 N 个 attention 层"的地基）；最后把视图交给 writer store。
曾经的 `if self._canon is not None:` 守卫删了：事实链是 _canon 只有
worker 构造会赋值而这个 hook 只有 worker 收得到，守卫两边永远不会
分开走。它真防御的东西只有一件事——退化实例装作注册成功然后全程
静默不干活，这比 AttributeError 可怕多了。

**保存段的按组拆分**是回归测出来的真 bug，值得一提：执行序穿插着三
个 mamba 组，一段排头的 mamba 层可能横跨三个组。旧代码一股脑用第一
组的 label 提交整段，结果第二三组的边界从来没写进台账，明明保存成
功却全员 MISS。修复就是把段内再按组分拨。

**`start_load` 的 GDN 屏障**是一次交换：GDN 层在 vLLM 里没有 hook，
如果开头不等它们，就没有第二个机会等了。所以在 start_load 结尾对所
有 mamba 任务 host-block 一下。代价是损失一点重叠（一共就几块几十
MB，相对一次 forward 很小），换来的是不存在"GDN 层没等到就跑了"
这种事故，也不需要一个"哪个 attention 层负责哪个 mamba 层"的决策机
构。简单压倒聪明。

**保存侧全靠 `save_kv_layer` + `wait_for_save` + `get_finished` 三级
接力**：每个 attention 层跑完当场提交它的页（和它前面那段 mamba 段
一起提交——那些层的 kernel 早就跑完了，数据早就定型）；forward 结束
后 wait_for_save 补交没人管的尾巴；真正的等待全部发生在
get_finished（步骤间隙，每步一次，逐个检查写完了没）。任何一处都
不阻塞计算的关键路径。

**双重 drain bug** 修在 get_finished 里，原因值得记一笔：两个请求共
享同一段边界时（并行 decode 很常见），去重后的写任务挂在两个人的账
上。第一个请求结账时引擎会把任务标记完成（ctx 清 None）；第二个请
求再拿同一份任务去问引擎，native 层断言直接拍死 worker。修复就是结
账前看一眼 ctx 是否已被清空，清了说明这笔账别人付过了，直接划掉。

**保存原子性的一句话版本**：一个组的所有层在一次调用里写齐才算提
交，没有"先写数据再发布"的第二阶段——不存在只写了一半还能被人读
到的中间态。半截边界的处理是全文件唯一不发火的保存异常（warning +
跳过）：因为它天然无害，那些块后来查起来就是 MISS，重算一次而已。

## 8. 两轮清理改了什么、凭什么

| 改动 | 凭什么 |
|---|---|
| `if self._canon is not None:` 守卫 | 条件恒真；且真触发时它选的是"静默装成功"，不如自然炸 |
| `_now()` 时间包装 | 就俩调用点，函数体里还局部 import time；直呼 time.monotonic() |
| `add_request` 方法 | 生产无人调用，纯测试 API |
| `get_page`/`_page_parts` | 生产只有调试转储在用；并入 page_view_parts 一条路 |
| 块表长度预检 continue | 不可达分支；且失败方式是静默拿半张表 |
| 手抄的视图平铺推导 | 和 _flat_views 一模一样，留一份 |
| 注册三层委托 | 中间层纯粹转手，两层足够 |
| split-K/V 注释里的旧布局 | v0.23 不是 [2,N,...]；算法本身没动 |
| compute_namespace 整个函数 | sha256 命名空间是已删 HybridStore 的孤儿；main 对 dtype/tp 串味裸奔，单独给 hybrid 上锁超出 GDN 范围 |
| CacheKey 的 namespace/tp_size/rank 字段 | tp 已在 namespace 里；恒常量字段无身份作用；rank 编进 label 是两边目录各自相等的自娱自乐，连 _worker_key 一起删 |
| __init__ 占位双写字段 | 每字段单一赋值点；构造缺 config 立刻在最短路径炸 |

一句话总结删的标准：**没有一条删除碰到了"防静默错数据"的防线；被
删的全是够不着真实事故的代码。**
